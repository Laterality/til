## 개요

### Kubernetes의 객체

#### Kubernetes 객체 관리

##### 선언적 객체 구성

선언적 객체 구성을 사용중일 때는, 사용자가 로컬에 저장된 객체 구성 파일에 작업하지만 사용자는 파일에 가해지는 작업을 정의하지는 않는다. 생성, 갱신, 삭제 작업은 `kubectl`에 의해 자동으로 객체별로 감지된다. 이는 서로 다른 작업들이 서로 다른 객체에 대해 필요할 수 있는 디렉터리에 대해 동작할 수 있게 한다.

> [!NOTE]
>
> 선언적 객체 구성은 변경사항이 객체 구성 파일에 다시 병합되지 않은 경우에도 다른 기록자에 의해 만들어진 변경을 유지한다. 이는 전체 객체 구성을 `replace` API 작업 대신 관측된 차이점에만 쓰도록 `patch` API 작업을 사용함으로써 가능하다.

###### 예시

`configs` 디렉터리의 모든 객체 구성을 처리하고 살아있는 객체를 생성하거나 패치한다. 먼저 `diff`로 어떤 변경이 만들어질지 확인한 다음 적용할 수 있다:

```bash
kubectl diff -f configs/
kubectl apply -f configs/
```

재귀적으로 디렉터리를 처리한다:

```bash
kubectl diff -R -f configs/
kubectl apply -R -f configs/
```

###### 트레이드 오프

명령적 객체 구성과 비교한 장점:

- 살아있는 객체에 직접 반영된 변경은 구성 파일에 병합되지 않더라도 유지된다.
- 선언적 객체 구성은 디렉터리에 작업하는 것과 객체별로 자동으로 작업 유형(생성, 패치, 삭제)을 감지하는 것에 있어 더 나은 지원을 제공한다.

명령적 객체 구성과 비교한 단점:

- 선언적 객체 구성은 디버깅과 예기치 않은 결과가 발생했을 때 이를 이해하기가 더 어렵다.
- 차이점을 사용한 부분 변경은 복잡한 병합과 패치 작업을 만들어낸다.
