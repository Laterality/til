## 개요

### Kubernetes의 객체

#### Kubernetes 객체 관리

##### 명령적 객체 구성

명령적 객체 구성에서는 kubectl 커맨드가 작업(생성, 대체 등)과 선택사항으로 플래그와 적어도 하나의 파일 이름을 지정한다. 지정된 파일은 YAML이나 JSON 형식으로 객체의 전체 정의를 포함해야 한다.

객체 정의의 더 자세한 내용은 [API 레퍼런스][k8s-reference-generated-kubernetes-api-v-1-36]를 참고하라.

> [!WARNING]
>
> 명령적 `replace` 커맨드는 구성 파일에 누락된 객체에 대한 모든 변경사항을 버리고` 기존 스펙을 새로 전달된 것으로 대체한다. 이 접근 방식은 스펙이 구성 파일과 독립적으로 갱신되는 리소스 유형에 쓰여서는 안된다. 예를 들면 `LoadBalancer` 유형의 서비스는 `externalIPs`가 클러스터에 의해 구성 파일과 독립적으로 갱신된다.

###### 예시

구성 파일에 정의된 객체를 생성한다:

```bash
kubectl create -f nginx.yaml
```

두 구성 파일에 정의된 객체들을 제거한다:

```bash
kubectl delete -f nginx.yaml -f redis.yaml
```

구성 파일에 정의된 객체를 살아있는 구성에 덮어써서 갱신한다:

```bash
kubectl replace -f nginx.yaml
```

###### 트레이드 오프

명령적 커맨드와 비교한 장점:

- 객체 구성이 Git과 같은 소스 컨트롤 시스템에 저장될 수 있다.
- 객체 구성을 변경 전에 검토하고 감사 추적과 같은 프로세스에 통합할 수 있다.
- 객체 구성이 새 객체를 생성하기 위한 템플릿을 제공한다.

명령적 커맨드와 비교한 단점:

- 객체 구성이 객체 스키마에 대한 기본적인 이해를 필요로 한다.
- 객체 구성이 YAML 파일을 작성하는 추가 단계를 필요로 한다.

선언적 객체 구성과 비교한 장점:

- 명령적 객체 구성 동작이 더 단순하고 이해하기 쉽다.
- Kubernetes 버전 1.5부터 명령적 객체 구성이 더 성숙했다.

선언적 객체 구성과 비교한 단점:

- 명령적 객체 구성은 디렉터리가 아닌 파일에 대해 가장 잘 동작한다.
- 살아있는 객체에 대한 변경은 구성 파일에 반영돼야 한다. 그렇지 않으면 다음 변경시 손실된다.
