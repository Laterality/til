## 클러스터 아키텍처

### 노드와 컨트롤 플레인 사이의 통신

#### 노드에서 컨트롤 플레인으로

Kubernetes는 "허브-앤-스포크" API 패턴을 가지고 있다. 노드(나 노드가 실행하는 파드)로부터의 모든 API 사용은 API 서버에서 끝난다. 다른 컨트롤 플레인 구성 요소 어느것도 원격 서비르르 노출하도록 설계되지 않았다. API 서버는 안전한 HTTPS 포트(주로 443)로 하나 이상의 클라이언트 [인증][k8s-reference-access-authn-authz-authentication]과 함께 원격 커넥션을 리스닝하도록 구성된다. 특히 [익명 요청][k8s-reference-access-authn-authz-authentication-anonymous-requests]이나 [서비스 계정 토큰][k8s-reference-access-authn-authz-authentication-service-account-tokens]이 허용된 경우 하나 이상의 [인가][k8s-reference-access-authn-authz-authorization]가 활성화돼야 한다.

Node는 유효한 클라이언트 크리덴셜로 API 서버에 안전하게 연결하기 위해 클러스터를 위한 공개 루트 [인증서][k8s-tasks-tls-managing-tls-in-a-cluster]와 함께 프로비저닝돼야 한다. 좋은 접근 방식은 클라이언트 인증서 형태로 kubelet에 클라이언트 크리덴셜을 제공하는 것이다. kubelet 클라이언트 인증서의 프로비저닝 자동화는 [kubelet TLS 부트스트래핑][k8s-reference-access-authn-authz-kubelet-tls-bootstrapping]을 참고하라.

API 서버에 연결하고자 하는 [Pod][k8s-concepts-workloads-pods]는 서비스 계정을 활용해 Kubernetes가 자동으로 공개 루트 인증서와 유효한 bearer 토큰을 파드 생성시 주입할 수 있게 함으로써 안전하게 연결할 수 있다. (`default` 네임스페이스의) `kubernetes` 서비스는 ([`kube-proxy`][k8s-reference-command-line-tools-reference-kube-proxy]를 통해)API 서버의 HTTPS 엔드포인트로 리다이렉트되는 가상 IP 주소로 구성돼 있다.

컨트롤 플레인 구성 요소들도 안전한 포트를 통해 API 서버와 통신할 수 있다.

결과적으로, 노드와 노드에서 실행중인 파드로부터 컨트롤 플레인으로 연결을 위한 기본 운영 모드는 기본적으로 안전하며 신뢰할 수 없거나 공개 네트워크를 통해서도 실행할 수 있다.
