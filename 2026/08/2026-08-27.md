## 개요

### Kubernetes의 객체

#### 스토리지 버전

Kubernetes API 서버는 etcd와 호환되는 기반 저장소(대체로 기반 스토리지는 etcd 자체)에 의존해 객체를 저장한다. 각 객체는 해당 API 유형의 특정 버전을 사용해 직렬화된다. 예를 들어, ConfigMap의 v1 표현이 있다. Kubernetes는 *스토리지 버전*이라는 용어를 사용해 클러스터에 객체가 저장되는 방법을 설명한다.

Kubernetes API는 자동 변환에도 의존한다. 예를 들어, HorizontalPodAutoscaler를 가지고 있다면 v1과 v2 어느 HorizontalPodAutoscaler API를 사용하든 HorizontalPodAutoscaler와 상호작용할 수 있다. Kubernetes는 각 API 호출을 변환해 클라이언트가 실제로 직렬화되는 버전을 보지 않도록 할 책임을 갖는다.

클러스터 관리자의 경우, 객체 스토리지 버전은 객체의 API 표현을 스토리지 백엔드의 실제 인코딩과 연결하기 때문에 중요한 개념이다. 암호화나 API 폐기와 같이 객체의 기반 바이너리 인코딩을 신경써야 하는 경우 중요하다.

같은 API는 API 서버가 이후에 객체 스키마로 변환할 수 있는 여러 스토리지 버전을 가질 수 있다. 해당 객체의 일부분인 단일 객체는 어느 때든 하나의 스토리지 버전만을 가져야 한다. 즉, API 서버는 객체의 바이너리 인코딩을 알고 있고 저장된 모든 버전을 객체의 API 표현으로 동적으로 변환할 수 있다.

객체의 버전은 스토리지 버전과 완전히 별개다. 예를 들어, 같은 리소스의 `v1alpha1`과 `v1beta1` API 객체는 두 객체 사이에 스토리지 버전이 갱신되지 않는 한 스토리지에서 똑같이 인코딩된다.
