## 개요

### Kubernetes의 객체

#### 필드 선택자

##### 마감자(Finalizer)

###### 마감자의 동작 방식

매니페스트 파일을 사용해 리소스를 만들 때 `metadata.finalizers` 필드에 마감자를 명시할 수 있다. 리소스 삭제를 시도하면 삭제 요청을 처리하는 API 서버는 `finalizers` 필드를 인지하고 다음을 수행한다:

- 객체에 `metadata.deletionTimestamp` 필드를 삭제를 시작한 시간으로 추가해 수정한다.
- 자신의 `metadata.finalizers` 필드의 모든 항목이 제거될 때까지 객체가 제거되는 것을 막는다.
- `202` 상태 코드(HTTP "Accepted")를 반환한다.

해당하는 마감자를 관리하는 컨트롤러는 객체의 `metadata.deletionTimestamp`가 설정돼 객체의 삭제가 요청됐음을 알게 된다. 이후 컨트롤러는 리소스에 명시된 마감자의 요구사항을 만족시키려고 시도한다. 매번 마감자 조건이 만족되면 컨트롤러는 리소스의 `finalizers`에서 해당하는 키를 제거한다. `deletionTimestamp` 필드가 설정된 채 `finalizers` 필드가 비어 있는 객체는 자동으로 제거된다. 마감자를 사용해 관리되지 않는 리소스의 삭제를 방지할 수도 있다.

마감자의 흔한 예시는 `PersistentVolume`을 실수로 삭제하는 것을 막는 `kubernetes.io/pv-protection`이다. `PersistentVolume` 객체가 Pod에 의해 사용중인 경우, Kubernetes는 `pv-protection` 마감자를 추가한다. 이 `PersistentVolume` 삭제를 시도하면 `Terminating` 상태로 진입하지만 마감자가 존재하기 때문에 컨트롤러는 이를 삭제할 없다. `PersistentVolume`을 사용하는 Pod가 정지하면 Kubernetes는 `pv-protection` 마감자를 정리하고 컨트롤러가 볼륨을 삭제한다.

> [!NOTE]
>
> - 객체를 `DELETE`할 때, Kubernetes는 해당 객체에 삭제 타임스탬프를 추가하고 삭제를 보류중인 해당 객체에 대한 `.metadata.finalizers` 필드 변경을 즉시 제한하기 시작한다. 기존 마감자를 제거(`finalizers` 목록에서 엔트리를 제거)할 수는 있지만 새 마감자를 추가할 수는 없다. 또한 `deletionTimestamp`가 한 번 설정되면 이를 수정할 수도 없다.
> - 삭제가 요청되면 이 객체를 되살릴 수는 없다. 유일한 방법은 이를 삭제한 뒤 비슷한 새 객체를 만드는 것이다.

> [!NOTE]
>
> 커스텀 마감자 이름은 `example.com/finalizer-name`처럼 **반드시** 공개적으로 자격을 갖춘(qualified) 마감자 이름이어야 한다. Kubernetes는 이 형식을 강제한다. API 서버는 자격을 갖추지 않은 마감자 이름이 객체의 커스텀 마감자를 쓰는(write) 것을 거부한다.
